## 全体構成

フロントエンド（Vue.js の SPA）と、別プロセスで動くバックエンド（FastAPI）が HTTP（JSON）で通信する。データは PostgreSQL のスキーマ `coffee_ledger` に置く。

```
ブラウザ ──(SPA)── frontend（Vue.js / TypeScript）
                      │ fetch（JSON）
                      ▼
                   backend（FastAPI / Python） ──── PostgreSQL（スキーマ coffee_ledger）
                      │
                      └── backend/log/（ログファイル）
```

- 配置: `src/features/coffee-ledger/{frontend,backend,tests}`
- 参考実装: `sample/coffee-ledger`。構成・業務ロジック・画面は参考実装に合わせる。ただし次はルールに合わせて変える。

| 項目 | 参考実装 | 本設計 |
|------|----------|--------|
| 配置 | `sample/coffee-ledger/` | `src/features/coffee-ledger/`（`rules/02-project.md`） |
| DB 接続の設定名 | `Server` / `Database` / `Port` / `Username` / `Password` | `DB_SERVER` / `DB_DATABASE` / `DB_PORT` / `DB_USERNAME` / `DB_PASSWORD`（`specs/templates/backend.env.example`） |
| 接続先 DB | `cptestdb`（ユーザ `cptest`） | `tstdb`（ユーザ `tstuser`）（`rules/13-db.md`） |
| ログ | ファイルへの業務ログなし。gunicorn のログは `/var/log/coffee-ledger/` | `backend/log/` にローテーション付きで出力（`rules/16-logging.md`） |
| 公開 URL | ルート（`/`） | `/portal_coffee_ledger/`。Vite の `base` と `createWebHistory(import.meta.env.BASE_URL)`（`rules/17-nginx-deploy.md`） |
| CORS の資格情報 | 許可する | 許可しない（認証しないため。`rules/12-backend.md`） |
| SQL ファイル | 3 ファイル（002・003 は 001 と重複を含む追加分）。起動時に自動で実行 | 初期構築用 SQL とマイグレーション用 SQL に分け、手動で実行する（後述の「DB の構築」、詳細は `db-design.md`） |
| API の公開パス（本番） | `.env.production` に `/api` と記載 | 引き続き `.env`（`.env.production`）の `VITE_API_COFFEE_LEDGER_URL` で設定する。コードには書かない |
| テスト | なし | `tests/` にバックエンドの業務ロジックのテストを置く |

参考実装の DB にある既存データは移行しない。新しい DB に初期構築用 SQL で空の状態から作る。

## フロントエンド設計

### 主要な画面と役割

| 画面 | パス | 役割 | 関連要件 |
|------|------|------|----------|
| 一般画面 | `/` | 一杯単価・現在日時・利用中の人の一覧を表示し、飲用・支払の記録と取り消しを行う | REQ-001〜006 |
| 管理パスワード入力画面 | `/unlock` | 管理機能に入る前に管理パスワードを確かめる | REQ-007 |
| 管理トップ画面 | `/admin` | 一杯単価、徴収状況、金庫収納、金庫操作、DB の整理を扱う。下位画面への入口 | REQ-008〜011、REQ-022 |
| 人の管理画面 | `/admin/people` | 人の登録・利用停止・表示順の変更、人の記録の参照、未払いの修正 | REQ-012〜016 |
| 集計画面 | `/admin/summary` | 現在の 3 つの金額と、金額の推移を表示する。金銭の動きを CSV でダウンロードさせる | REQ-017、REQ-023 |
| 操作記録画面 | `/admin/operations` | 操作記録を新しい順に表示する | REQ-018 |

パスは公開 URL（`/portal_coffee_ledger/`）からの相対パスである。

- 本番: `npm run build` で `dist/` を作り、`rules/17-nginx-deploy.md` のディスク配置（ドキュメントルートの `features/coffee-ledger/`）へコピーする。

### モジュール構成（`frontend/src/`）

| モジュール | 役割 |
|------------|------|
| `main.ts` | アプリの生成、ルータと CSS の組み込み |
| `App.vue` | 殻。ヘッダ（`AppNav`）とルータの表示領域を並べる |
| `router.ts` | 画面とパスの対応。遷移前に管理パスワードの入力済みかを確かめ、未入力なら管理パスワード入力画面へ（入場先を引き継ぐ）。管理機能の外へ出たら入力済みの状態を解く |
| `adminGate.ts` | 管理パスワードの入力済み状態（メモリ上のみ）、入力値の照合、入場先の妥当性確認（管理機能内のパス以外は管理トップにする） |
| `api.ts` | API 呼び出しを 1 か所にまとめる。キャッシュを使わない。失敗時は API のエラー（コードとメッセージ）を投げる。通信失敗時は「通信に失敗しました。」。CSV は本文をファイル（Blob）として受け取り、応答の `Content-Disposition` からファイル名を取り出す |
| `download.ts` | 受け取ったファイル（Blob）を、指定のファイル名でブラウザにダウンロードさせる（一時的な URL を作ってリンクを押し、後で解放する） |
| `types.ts` | API の応答の型 |
| `format.ts` | 日本時間の日時の整形、金額の整形（`1,234円`）、今日の日付、支払額の 10 円刻みの増減（REQ-005） |
| `style.css` | 全画面共通の見た目（`rules/15-ui-style.md`） |
| `views/` | 画面ごとのコンポーネント（上表の 6 画面）。データの読み込み、操作の実行、処理中の二重操作防止、エラー表示を受け持つ |
| `components/` | 画面を構成する部品。表示と入力の検証だけを受け持ち、操作はイベントで画面へ通知する（API は呼ばない） |

画面の状態は各画面コンポーネントが持つ。状態管理ライブラリは使わない。操作が成功したら、関係する表示を API から読み直す。

## バックエンド設計

### 起動方法

- 開発: `src/features/coffee-ledger/backend/` に `venv/` を作り、`requirements.txt` を入れる。venv を有効化し、`uvicorn app.main:app --port 8010 --reload`。
- 本番: 同じ venv の gunicorn（uvicorn ワーカー）で `127.0.0.1:8010` に起動する起動スクリプト `start_gunicorn.sh` を置く。gunicorn のアクセスログとエラーログも `backend/log/` に出す。
- 起動時に SQL は実行しない。DB は次の「DB の構築」で事前に用意する。

### DB の構築（`backend/sql/`）

SQL は用途で 2 つに分け、`psql` で手動実行する。ファイルの中身（テーブル定義）は `db-design.md` に従う。

| 種類 | 置き場所 | 用途 |
|------|----------|------|
| 初期構築用 | `backend/sql/init/` | 空の DB に、スキーマ `coffee_ledger` と最新のテーブル一式を作る。新しい環境ではこれだけを実行する |
| マイグレーション用 | `backend/sql/migrations/` | 構築済みの DB を、テーブル定義の変更に追従させる差分。ファイル名の先頭に通し番号（`001_…sql`）を付け、番号順に実行する |

- テーブル定義を変えるときは、マイグレーション用 SQL を追加し、同じ変更を初期構築用 SQL にも反映する（初期構築用 SQL は常に最新の定義を表す）。
- どちらの SQL も、再実行しても壊れないように書く（`IF NOT EXISTS`、`DROP … IF EXISTS` など）。
- 初版の時点では、マイグレーション用 SQL は無い（初期構築用 SQL が最新の定義）。

### 設定値（`backend/.env`）

`specs/templates/backend.env.example` に従う。認証しないため `DEBUG_USER` と `SESSION_TIMEOUT_MINUTES` は持たない。

| 名前 | 内容 |
|------|------|
| `DB_SERVER` / `DB_PORT` / `DB_DATABASE` / `DB_USERNAME` / `DB_PASSWORD` | 接続先 DB |
| `CORS_ORIGINS` | 許可するフロントのオリジン（カンマ区切り、`*` は不可） |
| `LOG_MAX_BYTES` / `LOG_BACKUP_COUNT` | ログのローテーション |

必須の設定値が無いとき、起動時にエラーで止める。

### モジュール構成（`backend/app/`）

| モジュール | 役割 |
|------------|------|
| `main.py` | アプリの生成。ミドルウェア（DB 接続、CORS）、例外ハンドラ、ルータの登録 |
| `config.py` | `.env` の読み込みと設定値の取得 |
| `db.py` | DB 接続。要求ごとに接続を開き、応答が成功（400 未満）ならコミット、失敗ならロールバックして閉じる。DB の整理用に、トランザクションを使わない（autocommit の）接続も作れるようにする |
| `errors.py` | 業務エラー（HTTP ステータス、エラーコード、日本語メッセージ）と、共通のエラー応答形式への変換。入力の型不正は入力エラー、想定外の例外は「処理に失敗しました。」にする |
| `logging_setup.py` | ログの出力先（`backend/log/coffee-ledger.log`）、ローテーション、1 行の形式（日本時間の日時・区分 INF/WRN/ERR/DBG・メッセージ） |
| `timeutil.py` | 日本時間の現在日時、日時の文字列化 |
| `routers/` | エンドポイントの定義。要求の形の検証（余分な項目は不可、数値は厳密な整数）だけを行い、`services/` を呼ぶ。対象ごとに分ける（人、飲用、支払、一杯単価、徴収・金庫収納、金庫操作、未払い修正、集計・CSV 出力、操作記録、DB の整理） |
| `services/` | 業務ロジック。`routers/` と同じ単位に分け、金額の計算は `balances.py` にまとめる。操作記録の追加は `operations.py` にまとめる。CSV の組み立ては `summary_csv.py`、DB の整理は `maintenance.py` に置く |

### 業務ロジック

**金額の計算（`balances.py`）** — 金額は記録から毎回計算し、残高を列として持たない。

- 未払い代金（人ごと）= 取り消していない飲用の単価合計 − 取り消していない支払の合計 + 未払い修正の（修正後 − 修正前）の合計。0 未満は 0。
- 未徴収金額 = 全員（利用停止した人を含む）の未払い代金の合計。
- 徴収済み金額 = 最後の金庫収納の日時より後に記録された、取り消していない支払の合計（金庫収納が無ければ全合計）。
- 金庫金額 = 金庫収納の合計 + 金庫操作の入金合計 − 出金合計。0 未満は 0。

**各操作の流れ** — いずれも 1 要求 = 1 トランザクションで、記録と操作記録を同じトランザクションで書く（REQ-018、REQ-020）。

| 操作 | 流れ | 拒否する条件 |
|------|------|--------------|
| 飲用の記録 | 人を行ロック → 一杯単価を取得 → 単価を写して飲用を追加 | 人が無い、利用停止済み、単価が未登録 |
| 飲用の取り消し | 人を行ロック → 飲用を行ロック → 未払い代金を計算 → 取り消し日時を入れる | 飲用が無い・他人のもの、取り消し済み、取り消すと未払い代金が 0 未満 |
| 支払の記録 | 人を行ロック → 未払い代金を計算 → 支払を追加 | 金額が 1 未満、未払い代金が 0、金額が未払い代金を超える |
| 支払の取り消し | 人を行ロック → 支払を行ロック → 取り消し日時を入れる | 支払が無い・他人のもの、取り消し済み |
| 一杯単価の保存 | 単価を行ロック → 無ければ登録、あれば変更（変更前の額を操作記録に残す） | 金額が 1 未満 |
| 金庫収納 | 金庫用のロック → 徴収済み金額を計算 → その額で金庫収納を追加 | 徴収済み金額が 0 |
| 金庫操作 | 入力を検証 → 金庫用のロック → 金庫金額を計算 → 金庫操作を追加 | 事由が空・200 文字超、入出金の別が不正、金額が 1 未満、出金額が金庫金額を超える |
| 人の登録 | 名前の前後の空白を除いて検証 → 人の表を排他ロック → 重複を確かめ、表示順の最大 + 1 で追加 | 名前が空・100 文字超、同名がいる |
| 人の利用停止 | 人を行ロック → 利用停止日時を入れる | 人が無い、利用停止済み |
| 表示順の変更 | 人の表を排他ロック → 渡された全員分の並びで表示順を 1 から振り直す（一意制約に触れないよう、先に全員を最大値より後ろへずらす） | 並びが空・重複あり、登録済みの全員と一致しない |
| 未払いの修正 | 入力を検証 → 人を行ロック → 現在の未払い代金を計算 → 修正前・修正後・事由を追加 | 新しい額が 0 未満、事由が空・200 文字超、現在と同じ額 |

- ロックにより、同じ人や金庫への同時操作でも金額の条件を破らない（REQ-021）。金庫用のロックはトランザクション単位の advisory lock とする。
- 表示順の変更は画面で隣と入れ替えた全員分の並びを受け取る。

**集計（REQ-017）** — 飲用・飲用の取り消し・支払・支払の取り消し・金庫収納・金庫操作・未払い修正を 1 つの出来事の列にまとめ、日時の古い順に並べて積み上げる。

- 飲用: 未徴収 +単価 ／ 飲用の取り消し: 未徴収 −単価
- 支払: 未徴収 −金額、徴収済み +金額 ／ 支払の取り消し: 未徴収 +金額。その支払が直前の金庫収納より後のものなら徴収済み −金額
- 金庫収納: 金庫 +金額、徴収済みを 0 に
- 金庫操作: 入金なら金庫 +金額、出金なら金庫 −金額
- 未払い修正: 未徴収 +（修正後 − 修正前）
- 各段階で 3 つの金額は 0 未満にしない。積み上げ後、新しい順に並べ替えて返す。先頭には現在の 3 つの金額（上記の計算）を添える。
- 同じ日時の出来事は、出来事の種類、記録の ID の順に並べる。

**金銭の動きの CSV 出力（REQ-023）** — 集計と同じ出来事と積み上げ結果を使い、サーバで CSV を組み立てて返す。

- 集計の計算（上記）をそのまま使い、日時の古い順に並べる（集計の表示とは逆順）。積み上げの値が集計の表示と一致する。
- 列: 日時、種類、名前、金額、入出金、事由、事由の日付、修正前の額、修正後の額、未徴収、徴収済み、金庫。該当しない列は空。
- 種類の表記は集計画面と同じ（飲む、飲用の取り消し、支払、支払の取り消し、金庫収納、金庫操作、未払い修正）。入出金は「入金」「出金」。
- 日時は日本時間の `YYYY-MM-DD HH:mm:ss`。金額は区切りなしの整数。
- 文字コードは UTF-8 で、先頭に BOM を付ける（Excel で文字化けしないため）。改行は CRLF。値にカンマ・引用符・改行があれば引用符で囲み、引用符は二重にする（RFC 4180）。Python の `csv` モジュールで書く。
- ファイル名 `coffee-ledger-YYYYMMDD-HHmmss.csv`（要求を受けた日本時間）を `Content-Disposition: attachment` で返す。フロントがファイル名を読めるよう、CORS でこのヘッダを公開する（`expose_headers`）。
- 読み取りだけで、操作記録には残さない。

**DB の整理（REQ-022）** — 台帳の 8 テーブルに `VACUUM (ANALYZE)` を実行する。

- `VACUUM` はトランザクションの中で実行できないため、要求ごとの接続（トランザクションあり）とは別に、autocommit の接続を開いて実行し、終わったら閉じる。
- 同時に 2 つ実行しないよう、その接続でセッション単位の advisory lock を試しに取り、取れなければ拒否する（`VACUUM_IN_PROGRESS`）。終わったらロックを放す。
- 所要時間（秒、小数第 1 位まで）を計って返す。
- 通常の `VACUUM` は台帳の読み書きを止めないため、実行中も一般機能は使える。`VACUUM FULL` は使わない。
- 台帳のデータを変えないため、操作記録には残さない。ログには要求・成功（所要時間）・失敗を出す。
- テーブルの所有者（接続ユーザ）で実行する。所有者でないと PostgreSQL はそのテーブルを飛ばすため、接続ユーザを `backend/.env` の DB ユーザ（初期構築用 SQL を実行したユーザ）にそろえる。

**日時** — 日時は日本時間で記録し、日時付きの ISO 8601 文字列（秒まで）で返す（REQ-019）。

### ログ（`rules/16-logging.md`）

- 業務の操作ごとに、要求の入力（人の ID、金額など判断に使う値）を INF、成功を INF、業務上の拒否を理由付きで WRN、想定外の例外を ERR で出す。
- 管理パスワードと DB のパスワードは出さない。
- ログファイル（`backend/log/`）はリポジトリに含めない。

### テスト（`tests/`）

- pytest で `backend` の `app` を import し、テスト用の DB で業務ロジックの主要な条件（金額の計算、拒否する条件、集計の積み上げ、CSV の中身と形式、DB の整理の実行）を確かめる。
- DB の整理はトランザクションの外で動くため、テストのロールバックでは戻らない。ただし台帳のデータを変えないので、開発用 DB のデータは変わらない。
- venv は `backend/venv/` を使う。

## 認証 / 認可

認証しない（`rules/14-security.md`）。API はすべて誰でも呼べる。

管理パスワード（REQ-007）は、誤操作を防ぐためのフロントエンドだけの入場確認である。入力済みの状態はブラウザのメモリにだけ持ち、再読み込みや管理機能の外への移動で解ける。API 側では判定しない。設定値はビルド成果物に含まれるため、秘密を守る手段としては扱わない。
